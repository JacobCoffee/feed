Reopening the PSF Grants Program with Twice-Yearly Funding Rounds

The Python Software Foundation (PSF) is excited to announce that the PSF Grants Program is reopening with a restructured schedule of two funding rounds per year. After the pause in 2025, and the special funding round held in 2026, the PSF is reopening the PSF Grants Program on an ongoing but restructured basis, with the budget reviewed annually. This approach aims to balance the sustainability of the program with our commitment to support the Python community through grants. 

The PSF is also happy to announce the upcoming funding round with a budget capped at $125,000 USD with a similar scope as the special funding round. We will be accepting applications from December 14 - January 4, for Conferences and Workshops that are scheduled between May 1, 2027, and September 30, 2027. Details on the restructured program are below. More information about the upcoming round will be published next week. 

Moving forward with twice-yearly funding rounds

The 2026 PSF Grants Program Funding Round was a success! The PSF is proud to have awarded 44 grants totaling approximately $60,000. The round also gave the Grants Work Group (GWG) and PSF staff the opportunity to explore the round-based process, in contrast to our old process of rolling applications, review, and awards. We received many questions and much feedback during the Grants Program Office Hour sessions and via email before and during the round. The most frequent question we received was “when will the next round of funding happen?”

While all the PSF could share at the time was that we hoped for the program to run on an ongoing basis, what we felt this question pointed to was the community’s call for reliability from the PSF Grants Program. The PSF wants to meet this call, both for the community’s sake and because reliability is one of the Program’s Guiding Principles. It also supports our Strategic Plan goal of fostering a thriving, connected global Python community. Based on that, we intend to run two funding rounds per year going forward, with the budget to be set in advance each year. That way, we can reliably offer grants to the community, and each round’s budget will determine how many grants we can award and at what size. We look forward to receiving community feedback so we can continue to improve the restructured PSF Grants Program as we move forward. 

Round timing

In order to get on a schedule aligned with PSF staff capacity around other projects throughout the year, (such as PyCon US, elections, and our end-of-year fundraiser), the upcoming second funding round will cover a five-month eligibility period of May 2027 through September 2027, meaning events taking place within that window can apply. After that, each round will cover six months, October to March and April to September. Rounds 3 and 4 below set the schedule we expect to follow going forward, repeating each year. The table shows the previous round, the upcoming round, and our expectations for the rounds after that.

The PSF expects questions and feedback about both the reopened Grants Program restructure as well as the upcoming funding round. Your feedback will help us improve during the process and for future rounds. There are multiple ways for you to reach out to us with your questions, feedback, and comments:

  • Discuss forum thread
  • Email grants@python.org
  • PSF Grants Office Hour sessions (more info below)

Final Thoughts and Thanks

This is yet another big change for the PSF Grants Program. It has moved from rolling applications, to a pause, to a special funding round, and now to a restructured schedule. The hope is to keep this format going forward, though we expect small changes and adjustments from round to round.

Thank you to the Python community for your patience as we work to make the program more viable for the PSF over the long term. We are grateful for your understanding and generous support, through your actions, words, and donations. We could not fulfill our mission without the community, or without each individual championing the PSF’s work. The PSF is so very grateful to be in community with each and every one of you.

Wing Python IDE Version 12.1.3 - November 24, 2026

Wing Python IDE version 12.1.3 has been released. This release and the hot fix updates made since Wing 12.1 was released:

  • Fix breakpoints, stepping, and exception reporting in Django templates, particularly with Python 3.12 and later
  • Make the Tasks Manager run independent tasks in parallel more often, and give it more ways to stop, resume, and redirect running tasks
  • Fix tasks or the Tasks Manager stalling, losing reports, or blocking commits in a number of cases
  • Improve Autonomous Peers and Send to Peer, including setting up a new peer by pasting the setup copied from another Wing
  • Improve Merge From Branch, which can hand its merge to the Tasks Manager
  • Let AI agents pull through Wing, using ssh passphrases Wing has stored or asks for, including on remote hosts
  • Bring back Subversion support, including for AI agents
  • Move the AI menu's items to the Project menu and tool Options menus
  • Fix Copilot, Cursor, Antigravity, OpenCode, and npm-installed agents on Windows
  • Fix Wing freezing after edits to files with test coverage, when a large wrapped file changes on disk, and when an AI task that changed large files ends
  • Fix Docker containers with Docker 29, debugging with spaces in the Python Executable path, and many other bugs

See the change log for details.

Wing 12.1 introduced guided autonomous development. You specify the goals, answer questions, and review results. AI agents design and write the code, unit tests, and documentation. Wing keeps you in control. Wing Pro 12.1 supports Claude Code, Codex, Antigravity, Copilot, Cursor, goose, OpenCode, and other ACP-compatible AI coding agents. See the list of Wing 12.1 features below for details.

New in Wing 12.1

Autonomous Development with the Tasks Manager

The new Tasks Manager is an agent that runs the Tasks tool's queues for you, so that development proceeds autonomously under your direction. You write tasks, mark the ones you want started as Ready, and review the results.

The Manager accepts anything from a bug report to a high-level specification for a new software project. It can break down larger tasks into a design and development plan. It decides task order, runs independent tasks in parallel, serializes those that are likely to edit the same files, and runs closely related tasks in shared session context. It can message a running agent to tell it about related work or new insights, redirect it if it goes astray, or stop it to resume later.

While the Manager is on, tasks run autonomously: Rather than stopping to ask questions or present intermediate results, each works as far as it can and ends with a report of the judgement calls it made along the way, and any questions it has left. A new Questions tab in the Tasks tool collects everything that is waiting for you, so you can provide answers in one place. Follow-up work and problems that agents notice as they run are added to the Plan tab of the Tasks tool as new tasks. The Manager may automatically start found tasks that are closely related to ongoing work; others wait for your review.

You stay in control of which work runs, how much the Manager can do, and how results are reviewed. Every change the Manager makes is listed and can be reverted or revised, even after changes have been committed. You can also talk to the Manager to ask about the status of development or give it special instructions about your development workflow.

Claude Code and Codex are best for autonomous development, since they self-check the safety of commands that they run. Antigravity, Copilot, and Cursor also work but don't implement the same level of safety checks. See AI Agent Safety in the AI Agent-Assisted Development chapter of the Wing manual for details and safety recommendations.

The Manager agent itself and queues in the Tasks tool can each use a different agent. You bring your own subscriptions or API keys for the agents you choose. Wing does not install agents or provide access to models.

Your Choice of AI Agent

Wing 12.1 adds support for other AI agents, now including Claude Code, Codex, Antigravity, Copilot, Cursor, goose, and OpenCode, either using their Textual User Interfaces (TUIs) or the Agent Client Protocol (ACP). AI agents can also set up how your code is run, such as a new program's main entry point, its run arguments, and its Python environment.

Improved User Interface

Modern Look: An optional new Modern look redesigns the toolbar, Preferences dialog, status bar, and tab overflow, and improves the display font. Two new display themes, Night Flight and Solo Flight, have been added. Themes can now incorporate transparent colors, be imported from VS Code, created from a small set of colors, or exported from your current color configuration.

New Project: The New Project dialog has been redesigned as a single page. Its Simple view asks only for the essentials, with a new directory, a virtualenv in the project's .venv, and a git repository as defaults, while All Options shows everything else. Progress is shown as a checklist in the dialog, and a failed step can be retried. Support for uv, Poetry, pipenv, micromamba, and pixi environments has been improved, and Wing offers to install a missing uv, Poetry, or pipenv.

Editor: Editors have a new Show Rendered toggle for Markdown, reST, HTML, SVG, images, and PDF files. The editor's scroll bar shows marks for diffs, search matches, and errors and warnings.

First Start: The first start of Wing is simpler, with a shorter Set Up Wing dialog and a Welcome to Wing window that leads with New Project, Open Folder, and Clone from GitHub. In Wing Pro and Wing Classic, trials now start automatically, with no sign-up, and all the license dialogs have been merged into one.

Improved Revision Control Integration

A new Project Log view in the version control tool shows the whole repository's history for git and Mercurial as a branch graph, with expandable diffs. You can sign in to GitHub, clone from a list of your repositories, and publish a new project to GitHub from New Project. Push Changes in the Project Status view pushes your work, and Merge From Branch on the toolbar merges another branch, in each case with an AI agent resolving any conflicts. Merge From Branch can also hand its merge to the Tasks Manager. AI agents can pull through Wing, using ssh passphrases that Wing has stored or asks for. The editor can also show annotations with commit message tooltips. Subversion is supported again, including for AI agents.

Other Improvements

Tasks Tool: Goals can be set aside for Later, and the Focus mode keeps just one goal open at a time. A new Incoming view collects tasks that agents found or proposed, for quick triage, and the Up Next view on the Execute tab shows what runs next in every queue. New Checklists hold recurring reviews, fixes, and release and deployment steps. A task's committed changes can be reverted, edited, or commented on, and every task has a short ID that links to the task wherever it is cited. Tasks can be sent to Wing on other machines, set up as Autonomous Peers, for example to check or fix something on another OS. A new peer can be set up by pasting the setup copied from another Wing. Agent sessions and the Tasks Manager continue on their own once a usage limit resets, and Send Note sends a message into a running task's session.

Other Changes: Source analysis is faster and its database is about 30% smaller. Wing offers to install Python if it finds no supported version, and to remove large cache directories left behind by older versions. Accept Debug Connections has moved to Project Properties so it is set per project. The AI menu's items have moved to the Project menu and the tool Options menus. Wing 12.1 also includes many bug fixes, particularly for remote development and Docker containers, debugging Django templates and free-threaded Python on Windows, AI agents on Windows, git worktrees and submodules, non-ASCII text on Windows, unit test discovery, and display themes.

Shed Skin restricted-Python to C++ transpiler v1.0 released!

I have just released version 1.0 of Shed Skin, a restricted-Python to C++ transpiler. It has taken a long time, in fact more than 20 years, to get to this point. I want to start by thanking all the people that have contributed over time. Leonardo Maffi helped out by testing in the first few years. IIRC, Harri Pasanen contributed extension module support. Johan Kristensen was instrumental in the move to Python 3. Jeremy Roquet and others helped to keep the project alive in my absense of several years. And in recent years, Shakeeb Alireza has been the main contributor, adding CMake (and hence good Windows) support, cleaning up the code and tests, and also contributing many good ideas.

So why release 1.0 now? Well, let's say that many things have finally come together. From a much improved type inference engine, to Unicode support, to much improved performance of generated code, to basically catching up with Python 3.15, a lot has happened over the past few months. Another thing that has happened (over the past few years?) is that C++ compilers have started to optimize away object allocations where possible. This has always been an achilles heel of Shed Skin, making it slower than for example PyPy for certain allocation-heavy programs. Regular allocations also seem to have become faster over time (under Linux at least). For my standard (of course highly biased!) performance plot, Shed Skin is now on average 5.0 times faster than PyPy, and in no case slower.

Something that I have to acknowledge also is the help of AI, more specifically Claude, to develop Shed Skin at a much more rapid speed than possible before. It has also been able to identify (and in many cases fix) about 500 bugs. We are all wondering about the future impact of AI of course, but let's hope that programming will remain a human hobby for a long time (the way chess is still enjoyable for humans, even though we totally suck at it.. :-)). But AI doesn't only help with development of Shed Skin, it can also help users to make their code Shed Skin compatible, and/or even submit issues/contributions. Thanks again to everyone who has contributed to the project, which has turned out to be my "life's work". Now that 1.0 has been reached, and with the advent of AI in programming, I don't know if I will continue to work on it intensively anymore though, without more/any community feedback or financial support, and spend more of my free time on other interesting projects. I will certainly try to keep it working, and do a yearly update for every new CPython release. I probably won't be able to help myself, but we will see! :-)

GitHub’s new “Security Advisory Permissions” feature is a massive win for OSS security sustainability

This week GitHub released a new feature for GitHub Security Advisories called "Security Advisory Permissions". The feature allows configuring repository teams and collaborators permissions to allow viewing, editing, and publishing GitHub Security Advisories. This feature has huge implications for the sustainability of security work for open source projects. Thank you to the folks involved at GitHub for adding this feature at a time when open source projects need all the help they can get for vulnerability work.

I was able to try this feature ahead of its public release through the Python Security Response Team (PSRT). The PSRT was invited to the private beta to test the feature and provide feedback. For the PSRT, this feature made triaging as a non-admin night-and-day easier, and we already have multiple members contributing to triage more actively and with renewed energy. Seriously, this feature is so good we're feeling excitement about triaging vulnerability reports. We need more of that kind of energy for security work in open source! 🔥

Sustainability and open source security

Before this feature was introduced only repository admins were able to view advisories by default, requiring adding other contributors as collaborators manually or using a bot, and only admins were able to edit and publish advisories.

What this meant concretely is that only the most privileged users could effectively triage vulnerability reports. Other would-be contributors were disempowered: they couldn't calculate severities, close duplicates or low-quality issues, assign CVE IDs, or stage and publish advisories. The tool enforced a narrow assumption about how security work had to be done and made vulnerability triage less sustainable for open source projects as a result.

I've argued that “open source security work isn't special”. All areas of open source contribution, security included, need to provide a smooth on-ramp for users with time, interest, and expertise to help projects. Without this model the work falls on a few of the most privileged contributors who are already contributing to other areas and don't necessarily have security expertise. This assumption also means projects can't ask for and receive help from third-parties, even when the energy and capacity for such support exists.

Right now open source projects are triaging more reports and publishing more advisories than ever before. This makes features like GitHub Security Advisories and similar features on other software forges invaluable. There is a lot more to do in this area, so I am hoping this is only the first step of many towards open source security work not being special.

DSF member of the month - Johannes Maron

For November 2026, we welcome Johannes Maron as our DSF member of the month! ⭐

Johannes has long been part of the Django community. He is a frequent contributor including project such as django-hijack which has more than 1.7K stars! He is part of the Django Review and Triage team. He is a DSF member since September 2025.

You can learn more about Johannes by visiting Johannes' website and his GitHub Profile.

Let’s spend some time getting to know Johannes better!

Can you tell us a little about yourself? (hobbies, education, etc)

Johannes Maron, or joe, born Johannes Hoppe in the GDR. Raised in West Germany only to return to his home state for uni. Studied software engineering at the Hasso-Plattner institute, dropped out and lived the start-up life. I still live in Potsdam and have the most amazing pug, son and wife (in alphabetical order).

I have an idea but where your nickname "codingjoe" comes from?

I am joe, and I code. Honestly, I was young, and I am just happy it's not naughtyb0i420 and thus never changed it.

How did you start using Django?

I started using Django for my very first company, I believe it was version 1.3? I have used it for every company I build ever since, and would always do it again.

What other framework do you know and if there is anything you would like to have in Django if you had magical powers?

Who said I don't have magic powers? The magic of contributing, we all have it and I made good use of it over the years. But my biggest dream would probably be a browser working group to overcome Django's JavaScript hesitance.

What projects are you working on now?

relay, a communication as a service provider. Think Sentry but for email, SMS, or VoIP. Or like AWS, but instead of shooting Katy Perry into space I hope to funnel the proceeds back into the community that it's build upon. Diamond sponsor or die is what I am aiming for. Until I get there, I am offering all services for free to non-profits or community projects.

Which Django libraries are your favorite (core or 3rd party)?

I can't live without dj_database_url and it's siblings like django-environ. 12-factor, always.

What are the top three things in Django that you like?

People, people, and people. You know who you are! <3

You have recently joined the Triage and Review team, congratulations! I know you are hosting now regular online events on reviewing PRs in Discord, could you tell us a bit more about this initiative?

Like all the best things in life, I just stumbled into it. I wanted to be more active and my PR queue was empty. I went on Discord asked, and people sent me more than I could review that day. I promised review them the following week and the wheel started turning. Fast-forward to some discussion on DjangoOnTheMed which gave me the confidence to make this a recurring thing. A small nudge from Tim (Schilling) to set up a Discord event and thus the FOSS Fridays were born.

What makes a good PR from a reviewer’s perspective? What’s the most common mistake you see?

It's less about the PR itself, but how it came to be. I maintain a lot of community projects where unsolicited feature PRs are all too common. It starts discussion at the wrong end and it requires a lot of mindful communication to convince authors to go back to the drawing board to reject a proposal. Also, "aura farming", patches to large project for the resume, is something I am not too fond of. Mainly because I know that once the PRs is merged, the maintenance burden will fall on me.

AI is more and more present in the tech world, especially in code contributions and reviews. How do you feel about that as a reviewer of Django?

I think besides the slop, there is one thing often overlooked. AI has decimated the entry level job market, so you have thousands of graduates turning to open-source to grind for XP. While I can genuinely emphasize, I think we need to steer that raw energy towards something better than generating even more code. Hence, FOSS Fridays. Gain XP and create value through review, not code. Given that AI does most of the corporate code writing these days, I believe that the best skill to acquire.

I know you are maintaining a lot of projects related to Django, thank you for your work. What made you create some projects in the first place, like django-health-check or django-hijack, for example?

The funny thing is, I created none of the once you mentioned. I started as a contributor and apparently did a good job at it. So the projects get transferred to me. My process is almost always the same, I build a company, need feature and if I find a package that is unmaintained, I offer my assistance. Only if the technology doesn't exist, I write my own package.

How do you manage to maintain so many projects at the same time?

My solution is twofold. If a project was taken over, I rewrite it from scratch. I am always aiming for an architecture, that can be easily extended via inheritance and avoid adding any settings. Once that is done, I resolve almost all issues with suggestions on how to implement those features within the users own project while constantly trying to improve the documentation. Most of my projects have zero open issues and PRs. The art of a "productive no" is something I could probably fill an entire bookshelf with.

You currently sponsor a lot of projects and people via GitHub (Django, Python, Homebrew and others). What’s your view on funding open source, and what would you tell companies that depend on it?

I think you need to separate two things. I use personal donations to show appreciation. They won't pay the bills, but the show maintainers that I care. You just need to decide if you need another streaming to pay for another billionaire's mega-yacht or if those 20 bucks are better spend on your first sponsorships.

Now, corporate sponsorships are a different beast. I believe they are fundamentally broken. For-profits are there to generate profit for their owners. But, they need employees to generate those profits even with all the AI in the world. The one thing you should always ask during an interview, is: "Does the company sponsor any open source projects?" Preferably late in the interview process. It costs nothing to ask, but the pressure will compound. ... Or you do it like my start your own company and do it differently 🤷

How do you envision the future of Django from your perspective?

I can't wait for Django version 2100. While I might not be around for that, I sure hope it'll happen. As for the DSF, I'd hope that it would eventually be able to build or acquire assets and accumulate wealth to be sponsorship independent. I know it sounds far-fetched, but it doesn't mean we shouldn't strive for a Django Software Fund.

After so many times in the Django community, what makes you stay?

I saved the stranges story for last. A long, long time ago, I was kindly offered a refund for my DjangoCon ticket, because of a tweet violating the CoC. Luckily I somehow managed dial down my ego for a minute and apologized like a grown up. The whole encounter changed how I perceived the subsequent conference and our industry as a whole and my role in it. Sometimes we learn more from our mistakes more than from our successes. The Django community has taught and challenged me so much over the years. All those experiences are now inseparable of who I am today. And even if I left, I hope to think I would carry those things with me always.

Is there anything else you’d like to say?

Thank you <3 and go Django 2100!

De-fanging dangerous triggers in GitHub Actions across an organization

Authors: Mike Fiedler, Seth Larson

On December 2, 2026, GitHub will start blocking the pull_request_target trigger by default in public repositories. If that sentence means nothing to you, this post is for you. If it fills you with dread, it is also for you.

The short version: a handful of GitHub Actions triggers let a stranger on the internet start a workflow that may have access to your secrets. On a GitHub Team or Enterprise plan, you can turn them off for every repository in your organization with one policy. On a Free plan, you can do it one repository at a time. Set the policy up, check what it would block, then enforce it.

Mike Fiedler, PyPI Safety and Security Engineer, and Seth Larson, Security Developer in Residence, have removed dangerous triggers and applied these policies to the Python Software Foundation (PSF) stewarded GitHub organizations (psf, python, pypi). They also wrote up technical documentation on how to roll these policies out to your own projects and organizations. The full details and technical documentation are available on the Alpha-Omega blog.

Have dangerous triggers caused real incidents?

Yes, repeatedly. A few that have affected projects hosted on PyPI directly:

  • Ultralytics, December 2024. The project's GitHub Actions workflows were compromised and the build cache was poisoned, which put malicious releases on PyPI. Seth wrote PyPI's analysis. William Woodruff's write-up traces the entry point to a pull_request_target workflow.

  • LiteLLM and Telnyx, March 2026. Malicious releases of both packages were published after an API token was exposed through an exploited Trivy dependency. StepSecurity traced the Trivy compromise back to a pull_request_target workflow exploited three weeks earlier. We worked with both maintainer teams on token rotation, release removals, and moving to Trusted Publishers, which both projects have since adopted.

  • elementary-data, April 2026. A workflow triggered by comments puts the comment text straight into a shell script. One crafted comment on a pull request ran with a token that could be written to the repository. The attacker used it to commit a malicious file and push a release tag, and the project's own release pipeline published the result to PyPI.

The maintainers behind these projects weren't careless. These triggers look harmless in a workflow file, and the unsafe version is one line away from the safe one.

Why are these triggers dangerous?

Insecure triggers can run workflows with access to your secrets, and a stranger can start them.

When someone opens a pull request from a fork, the pull_request trigger runs their code with a read-only token and no secrets. That's the safe one.

pull_request_target looks almost the same in a workflow file and behaves very differently. It runs with a read/write token and access to your repository and organization secrets. GitHub built it for chores like labeling pull requests from forks, where the workflow never touches the contributor's code. The trouble starts when a workflow checks out the pull request and runs it anyway:

on: pull_request_target
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
        with:
          # a stranger's code
          ref: ${{ github.event.pull_request.head.sha }}  
      # running with your secrets
      - run: make test

Anyone with a GitHub account can open that pull request. Their code now runs with your credentials. This is called a "pwn request", and GitHub's docs describe it as the root cause of multiple supply-chain compromises.

The issue_comment trigger carries the same risk. This trigger fires when anyone comments on an issue or pull request, and the workflow runs with the repository's token and secrets. Sometimes the victim is a "comment /test to run CI" bot that checks out the pull request and runs their code. Sometimes the workflow pastes the comment text into a templated shell command, and the comment turns out to inject different instructions into the workflow shell.

How did Alpha-Omega support this work?

Alpha-Omega is a fund and catalyst for sustainable open source security improvements. Alpha-Omega supports Mike's role as PyPI Safety & Security Engineer and Seth's role as Security Developer in Residence at the PSF.

That support is what gives us the time for the work behind this post:

  • Seth wrote PyPI's analysis of the Ultralytics attack

  • Mike and Seth worked with the LiteLLM and Telnyx maintainers during their incident, and wrote up the guidance for everyone else

  • Mike set up the event policy for the pypi GitHub organization

  • Seth is working to migrate the few remaining repositories using insecure triggers in the python GitHub organization before enabling the event policy

  • Mike and Seth wrote this guide so other organizations can do the same!
