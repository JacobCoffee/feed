reader 3.28 released – slow down, no AI redux

Hi there!

I'm happy to announce version 3.28 of reader, a Python feed reader library.

What's new? #

Here are the highlights since reader 3.26.

Slow down on errors and not modified feeds #

reader now slows down on errors by increasing the update delay exponentially, and matches the rhythm of the feed by adjusting the delay based on when the feed was last modified,1 in addition to the HTTP hint support added in previous versions.

This is part of a larger story about being polite to servers. Here, we still need logic to change feeds permanently in some cases, e.g. to handle permanent redirects, persistent errors, and repeated throttling. reader now stores detailed metadata about the last few updates of each feed, which will allow doing so in a future plugin.

New contributors #

Thank you to the new contributors that submitted pull requests to these releases!

Notably, you can now prevent automatic migrations by passing migrate=False to make_reader() or the equivalent CLI flag, and you can filter entries added_before a specific time (useful for a main page that updates only once a day, to prevent you from checking your feeds endlessly).

Want to contribute? Check out the docs and the roadmap.

Project infrastructure #

Earlier this year I added an AI policy banning LLM-generated content. To support it, there's now a pull request template asking contributors to confirm the PR does not contain any such content, and the readme mentions "no AI" as a deterrent.

reader stopped vendoring feedparser in 3.27, and recommends installing it from GitHub if you still want to benefit from the unreleased memory usage improvements.

Finally, Github Actions versions are now pinned and checked during CI.

Python versions #

reader 3.27 added support for Python 3.15 and PyPy 3.12, and dropped Python 3.11.

Hosted reader status update #

Speaking of, did I tell you I'm working on a hosted version of reader? :D

See also

  • Why another feed reader web app?
  • Why not just self-host it?
  • Public demo (no login needed).

Not a lot of progress since last time, because I got distracted with the pyinfra live demo, and with making sure multi-user feed updates continue to work with the upcoming feed reader behavior plugin.

That's it for now. For more details, see the full changelog.

What is reader? #

reader takes care of the core functionality required by a feed reader, so you can focus on what makes yours different.

reader allows you to:

  • retrieve, store, and manage Atom, RSS, and JSON feeds
  • mark articles as read or important
  • add arbitrary tags/metadata to feeds and articles
  • filter feeds and articles
  • full-text search articles
  • get statistics on feed and user activity
  • import / export feeds as OPML
  • automatically discover feeds in web pages
  • write plugins to extend its functionality

...all these with:

  • a stable, clearly documented API
  • excellent test coverage
  • fully typed Python

...and with no AI.

To find out more, check out the GitHub repo and the docs, or give the tutorial a try.

Why use a feed reader library? #

Have you been unhappy with existing feed readers and wanted to make your own, but:

  • never knew where to start?
  • it seemed like too much work?
  • you don't like writing backend code?

Are you already working with feedparser, but:

  • want an easier way to store, filter, sort and search feeds and entries?
  • want to get back type-annotated objects instead of dicts?
  • want to restrict or deny file-system access?
  • want to change the way feeds are retrieved by using Requests?
  • want to also support JSON Feed?
  • want to support custom information sources?

... while still supporting all the feed types feedparser does?

If you answered yes to any of the above, reader can help.

The reader philosophy #

  • reader is a library
  • reader is for the long term
  • reader is extensible
  • reader is stable (within reason)
  • reader is simple to use; API matters
  • reader features work well together
  • reader is tested
  • reader is documented
  • reader has minimal dependencies

#570: Free-Threaded Python

NumPy already releases the GIL. So threads should already pay off for your NumPy code, right? Christopher Ariza tested that. He summed the rows of a 10,000 by 10,000 array on Python 3.14. Sequential took 360 milliseconds. A thread pool took 373, slower than doing nothing. The same code on free- threaded Python 3.14t took 83.7 milliseconds. Free-threaded Python is officially supported as of 3.14. The GIL isn’t gone, though. It’s a zombie. Import one compiled package that hasn’t opted in, psycopg2 for example, and the GIL comes back for your entire process. You get a warning, not an error. Chris is the creator of StaticFrame and its C extension library ArrayKit. Human sorting, hardened

“Human sorting” is sorting strings (usually file names) so that any numbers in the names come out in the right order. For example, “file10.txt” should come after “file2.txt”, but regular sorting will put them in the wrong order. I’ve written twice before about the function to do this (Human sorting and Human sorting improved), but there’s more to say about it.

One effect of AI these days is bug reports for obscure edge cases. As a maintainer, it’s been a challenge first to read through them all, and then to decide which ones deserve a fix. It’s tempting to fix every little thing no matter how unlikely it is to happen in the real world. But every fix costs time, energy and focus. Every fix comes with risks in the form of new bugs or changed behavior. So some long-tail issues should be marked as “won’t fix.”

But this one intrigued me: if a file name includes a numeric component with 4301 digits, then the human sorting function fails. Buh?

Before we get to the current problem, here’s the original “buggy” code, slightly simplified:

def human_key(s: str) -> tuple[list[str | int], str]:

    """Turn a string into a sortable value that works how humans expect.



    "z23A" -> (["z", 23, "A"], "z23A")



    """

    def try_int(s: str) -> str | int:

        """If `s` is a number, return an int, else `s` unchanged."""

        try:

            return int(s)

        except ValueError:

            return s



    parts = re.split(r"(\d+)", s)

    split_key = [try_int(c) for c in parts]

    return (split_key, s)



def human_sorted(strings: Iterable[str]) -> list[str]:

    """Sort the given iterable of strings the way that humans expect."""

    return sorted(strings, key=human_key)

It splits the string into parts alternating between runs of digits and runs of non-digits. It uses try_int on all of them, which turns the digits into ints and leaves the non-digits as strings. That gives us a list of words and numbers that can be compared to do the sort we need.

The problem now is with that 4301-digit run. Since 2022, Python’s string-to-integer conversion has had a limit on the number of digits that can be converted. This is to prevent denial of service attacks based on the quadratic time to convert a string to an int. The default limit is 4300 digits. If a string is longer than that, int() raises a ValueError.

But we were counting on ValueError to mean “this isn’t an integer”, and to separate words from digits. Now that too-long number makes try_int return the string un-converted, and using it as a sort key will try to compare an int to a string, failing with:

TypeError: '<' not supported between instances of 'int' and 'str'

Of course, it’s absurd to be concerned that an actual file name will include a run of more than 4300 digits. But I’ve been tweaking this function over decades, and I like fiddling with it. The comments on the original post offered a number of alternative implementations, a few of which would have avoided this problem.

Rather than try to convert all of the parts of the name, we know from how re.split works that the parts will alternate between words and numbers, starting with a word even if it’s just an empty string. So we can attempt conversion only for the parts that we know are digits.

First, we replace try_int with a function to safely convert digit spans into numbers:

def number(s: str) -> float:

    """Convert s to a number with no errors."""

    try:

        return int(s)

    except ValueError:

        # This only happens if the number is too large to convert to an int.

        return float("inf")

Now we can create split_key differently by only converting the odd-numbered parts:

split_key = [(number(p) if i % 2 else p) for i, p in enumerate(parts)]

It’s tempting to check whether a part starts with a digit:

split_key = [(number(p) if p[:1].isdigit() else p) for p in parts]

But isdigit() gets us into Unicode difficulties because \d and isdigit() disagree on what count as digits. Something odd like "a1²b" would be split into ['a', '1', '²b'], and '²'.isdigit() is true, so now we’d be mistaking words for numbers.

Another even-odd approach, but it’s too fancy:

converters = itertools.cycle([str, number])

split_key = [fn(part) for fn, part in zip(converters, parts)]

In the end, though this is a long-tail bug, I fixed the human sort function; it was a tiny isolated fix. Also, I don’t like having a function that works only 99.9999% of the time. And maybe it’s still not done: there are probably other odd edge cases that could be a problem here. If I hear of those, I might make more fixes.

The AI fire-hose of issues and pull requests requires me to exercise and strengthen my “won’t fix” muscle. But I also get to choose where to make a fix just because it pleases me.

Update: Jeff Epler suggested a few clever alternatives. The 4300-digit limit is only applied to base 10 conversion. If we interpret digit spans as base 16, there’s no limit on length, and the resulting ints will sort the same as their base 10 counterparts. No helper function is needed at all. As an added bonus, there are now no floats, so the type hinting can be more straighforward. The result is satisfyingly compact:

def _human_key(s: str) -> tuple[list[str | int], str]:

    """Turn a string into a list of string and number chunks.



    "z23a" -> (["z", 35, "a"], "z23a")



    Runs of digits are converted using base 16 because it has no digit limit,

    and the numbers will sort the same as if they were interpreted as base 10.

    The original string is appended as a last value to ensure the key is unique

    enough so that "x1y" and "x001y" can be distinguished.

    """

    parts = re.split(r"(\d+)", s)

    split_key = [(int(p, base=16) if i % 2 else p) for i, p in enumerate(parts)]

    return (split_key, s)



def human_sorted(strings: Iterable[str]) -> list[str]:

    """Sort the given iterable of strings the way that humans expect.



    Numeric components in the strings are sorted as numbers.



    Returns the sorted list.



    """

    return sorted(strings, key=_human_key)

Another of his suggestions was to use a different int() substitute. We don’t need actual integers in the key, just something that will sort the same way as integers. His idea was to turn digit runs into a tuple of (length, value) with no conversion at all!

split_key = [

    (

        (len(p2 := p.lstrip("0")), p2)

        if i % 2 else p

    )

    for i, p in enumerate(parts)

]

I haven’t done timings of any of these solutions. This last solution avoids the quadratic time of integer conversion, but would likely be slower for the real-world data we find in file names.

Calvin #1: De-fanging dangerous triggers in GitHub Actions across an organization

  • GitHub will block pull_request_target by default in public repos starting Dec 2, 2026. GitHub announced this in its changelog on Nov 2; it isn't in effect yet. That default stops applying once you set your own event policy.
  • Two triggers are the main danger. pull_request_target and issue_comment both run with a token that can write to the repo and with the repo's secrets. The classic "pwn request" is a workflow that checks out a stranger's PR code and runs it.
  • It's not theoretical. Ultralytics (Dec 2024), LiteLLM and Telnyx via Trivy (Mar 2026), and elementary-data (Apr 2026), where a single crafted PR comment led to a malicious release on PyPI.
  • To get started, the first step is an Actions event policy. On GitHub Team or Enterprise, one org-wide policy allows only the triggers you expect: pull_request, push, release, repository_dispatch, schedule, workflow_dispatch, workflow_run.
  • Start in Evaluate mode. It blocks nothing and logs what would have been blocked under "Policy insights". Leave it on long enough to cover a release and your least frequent scheduled job.
  • Free plans have to do it repo by repo. You apply the same policy through gh api /repos/$repo/actions/policies. New repos have no policy until someone adds one.
  • Find what you have: gh search code pull_request_target path:.github/workflows --owner YOUR-ORG, also search for issue_comment and then zizmor to check each repo's workflows.

Michael #2: RQlite - The fault-tolerant relational database built on SQLite.

rqlite is a self-hosted distributed relational database built on SQLite and the Raft consensus protocol. It puts SQLite behind an HTTP API and replicates data across machines. For Python developers, the appeal is familiar SQL and lightweight deployment, with a database that can survive a server failure.

  • Keep SQLite's SQL, add high availability. A three-node cluster can survive one node failing, provided the remaining nodes can communicate.
  • Python applications send SQL and parameters over HTTP as JSON. Integrations include pyrqlite and sqlalchemy-rqlite; check client capabilities before migrating existing code.
  • Deployment is a single binary per node, with Docker and Kubernetes options. Features include full-text search, JSON support, SQLite extensions, change data capture, and automated cloud backups.
  • Replication does not scale writes. Every write goes through the leader and Raft log, adding network and disk overhead compared with standalone SQLite.
  • Transactions must fit within one HTTP request. You can execute a batch atomically, but cannot hold a transaction open across requests. Explicit BEGIN/COMMIT/ROLLBACK control is unsupported.
  • Read consistency is configurable: default Weak normally reads from the leader; Linearizable adds quorum checks; None permits potentially stale local reads. Stronger guarantees cost coordination.
  • Discussion angle: when does SQLite need clustering rather than just backups? Proposed demo: write from Python, stop the leader, then show the surviving cluster accepting requests after election.

Michael #3: diskcache-oxide now supports Django

diskcache-oxide plugs into Django’s existing cache framework for page caching, template fragments, low-level cache calls and sessions. Worker processes on the same machine share one cache on disk, with atomic counters across processes. The appeal is keeping Django’s familiar caching API without running Redis or Memcached.

  • Setup uses the package’s django extra, diskcache_oxide.DjangoCache as the backend, and an absolute directory for LOCATION. Existing Django cache calls stay the same; optional sharding spreads contention across multiple cache files.
  • Keep disposable pages separate from session state. The recommended configuration uses two aliases and directories: page-cache failures become misses or dropped writes, while session writes raise on failure and sessions are not evicted for size. The backend rejects session configurations that silently drop writes.
  • The companion Django example runs four Gunicorn workers and demonstrates cached views, template fragments, sessions and a shared visit counter. Response headers identify which worker answered, and multiprocess tests check concurrent increments, sessions across workers and caches opened before forking.
  • This shares a cache across processes on one machine, not across a fleet. Django’s get_or_set() can still compute twice when workers miss together. A cached view that reads sessions also needs vary_on_cookie to avoid serving one visitor’s personalized response to everyone.

Calvin #4: Muru: an AI-assisted Rust server for Python apps from mod_wsgi's creator

Simon Willison's post (repo: muruhq/muru · author's series: Twenty years of mod_wsgi)

  • What it is: Muru is Graham Dumpleton's successor to mod_wsgi, 20 years after he started writing mod_wsgi in December 2006. It's not an Apache module and not another server you put behind nginx. He means it to handle running a Python web app from your laptop through to production.
  • The parts: muructl is a single Rust binary that handles HTTP/1.1, HTTP/2, TLS, static files and compression, and never runs Python. A Python host process imports your app once and forks workers from it. A controller decides what runs and is never on a request's path.
  • It hosts more than WSGI: ASGI and gRPC too, all in one app. Requests can be handed from WSGI to ASGI, so an existing WSGI app can add websockets without a rewrite. Flask and Django run unmodified, e.g. muructl run mysite.wsgi:application.
  • Every deploy is a new release: a release starts next to the old one and traffic moves only once it's ready. If the new code won't even import, the old release just keeps serving. Even dev-mode auto-reload works this way, and the same mechanism gives you blue/green, canaries and rollback.
  • It understands Python apps: the access log splits waiting time (queue=, every thread was busy) from your code's time (app=), so you can tell "add capacity" from "fix slow code". Each scaling policy can scale workers to zero and optionally stop the host process too.

Deferred modules load separately in each worker, so they aren't shared through copy-on-write memory. Muru measures import costs per app instead of guessing.

  • The AI angle: Dumpleton says most of the code was written by AI, while he handles design, review and steering. It's about a month old, and he's in the Claude for Open Source Program. He doesn't accept patches: "don't send me a patch, just describe the problem." Abolish Lock Poisoning

Rust has a curious feature that I don’t think the language would land today, if it was not there for a long time: mutex poisoning. When some Rust code panics while holding a std::sync::Mutex, the mutex is poisoned. That means that any further call to lock() returns a PoisonError. The motivation for this feature is that an object might have some internal invariants that need to be upheld and panicking in the wrong moment might invalidate reasonable at and leave an object behind in a broken state.

Personally I absolutely hate this feature as it has bitten me so many times and I cannot once remember it helping me. The libs team is discussing making the non-poisoning locks the default in the next edition but entirely expectedly it has caused quite a few people to jump to the defence of the feature.

In this post I want to make my personal case why poisoned locks should either be entirely removed or be made the exception.

Primarily this is because I have yet to come across code in the wild that handles a poisoned lock correctly. On the other hand I have come across enough code that mishandles it and as a result behaves worse than a parking_lot lock would which does not support poisoning.

Josh Triplett put it quite strongly in a hackernews comment: “In the entire history of the standard library, we have never once seen a single report of anyone attempting to recover from poison.”

When a panic happens with a lock held, there are two reasonable reactions: shut the process down, or carry on and ignore the flag. With panic = "abort" you get the former and poisoning never comes up. From all the evidence I have seen, with unwinding, the idiomatic lock().unwrap() picks the worst option of all.

That’s because it neither stops the process nor lets it continue as it will turn every further lock into a panic with sometimes disastrous effects. But that is not the only issue with the system today. So here I want to share some of the issues and with some references to real world code of how people got bitten.

The Error Holds the Lock

One subtle aspect to the poisoning is that the PoisonError needs to hold the guard. That’s because in order to ignore the poison flag, you need to fetch the guard from the error object. Holding on to the error means holding on to the lock!

That can cause common code that does error wrapping / error conversions into a deadlock hazard. The innocent looking m.lock()? in a function returning Box<dyn Error> or similar keeps the mutex locked for as long as the error lives (#159930).

This can also happen with if let. For instance in cc-switch you can see that they had a test hung because a if let Ok(..) = lock() { .. } else { .. } fallback locked the same mutex again while the unnamed PoisonError from the condition still owned the guard. PC-AI had the same bug in a match arm. Another case can be found in ox-embed-server.

Panic To Outage

Deviously poisoning does not fail fast and done wrong, it fails forever. The original panic happens once, on one thread, often somewhere unrelated from future failures. Every later lock().unwrap() on that lock now however panics as well, and because so much Rust code survives panics (thread pools, request handlers, tokio tasks, FFI boundaries), the process stays up and becomes useless:

  • In RLS a failed cargo build panicked with ENV_LOCK held which made any subsequent runs impossible.
  • Mozilla’s application-services saw PoisonError rise to rank 5 in crash stats and moved to parking_lot after they concluded they did not benefit of poisoning handling.
  • A Neon safekeeper on staging failed every timeline lookup after a panic with a global lock held, and the original panic could not even be found in the logs.

While not live services, test suites show the same general issue. One failing test poisons a shared static and every test after it fails with PoisonError. This problem showed up for cargo, deno, polars and rustc itself.

Attempt At Recovery

If you recover with into_inner(), the flag stays set and every later access takes the recovery path again. And remember that for the first nine years of Rust after the poisoning feature landed, you could not even clear it as clear_poison arrived only in 1.77. Not clearing the flag means that potentially expensive side effects will happen from that point onwards:

goose-in-a-pond rebuilt its decoder state on every transcription after a single panic, librefang logged the same warning on every access, and a pool threw its model away on every return.

Nobody Relies on It, Not Even std

So who is handling poisonings? I’m really not sure, definitely not the standard library. Every place where the standard library’s own code ignores it. Standard I/O has done so since March 2015, two months before 1.0, because “any poison must have been the result of user code which the lock isn’t protecting”. A common issue with a lot of poisoning errors that never had anything to do with the mutex that was held.

Same with the panic output capture, the backtrace lock and the WASI environment lock. They all do the same and unsurprisingly there is an open PR to move std’s internal mutexes to nonpoison.

And I would argue the ecosystem has largely come to the same conclusion. Tokio’s own locks don’t poison. Internally it wraps the std one in an adapter that removes poison. When it landed Carl Lerche remarked “I rather pretend lock poisoning isn’t a thing.” In one case Eliza Weisman needed into_inner to unlink a waiter during drop, or “we’ll leave the list with a potentially dangling pointer”. I want to point to this in particular because this is a case where poisoning stood in the way of memory safety which is commonly argued as a reason you want poisoning.

Wasmtime, crossbeam-channel, tracing-subscriber always ignores lock poisoning. rust-analyzer switched to parking_lot after cancellation poisoned its solver like RLS did before. The parking_lot maintainer described it as an anti-feature that hurts usability and reliability to which I strongly concur.

Why Only Mutex?

Another aspect here is why this is done on Mutex but not on RefCell. Surely if the case for poisoning is that some code temporarily breaks an invariant, panics, and someone else observes the broken state, then this should apply to more cases.

Take the usual example that argues in favor of poisoning and replace Mutex with RefCell, and you have exactly the same problem. Threads are not needed at all and this is not hypothetical either as tokio catches every task panic. Paired with a LocalSet the panic comes back as a JoinError, the next borrow() succeeds and reads a null pointer exactly like the mutex example from the issue.

Given how much panic catching goes on in async code, much of which is !Send for performance reasons, I’m not even convinced that panics get caught more often in multi-threaded code yet nobody asks for RefCell to poison.

The standard library isn’t consistent with itself either as LazyLock poisons for good, OnceLock never poisons, Mutex poisons but lets you recover.

Also remember that poisoning only tracks panics and a more common early return has the same issue. The ? operator (as well as the try! macro before) that returns early from the middle of a critical section leaves the same broken invariant behind an unpoisoned lock.

Note also that the coupling of poisoning of mutexes is historical and an explicit Poison<T> type would allow you to opt into this for any interior mutability wrapper.

What I want

Personally I hope the rust team stabilizes std::sync::nonpoison, have std::sync::Mutex resolve to it by default. If someone wants poisoning add that separate Poison<T> wrapper then anyone who believes they need and can handle it, can opt into it for any type including RefCell or tokio threads.

What I think would be the worst of all outcomes is the counter-proposal is to keep poisoning but have lock() panic instead of returning a Result. That would only fix the held guard lock semantics, and to a smaller degree the ergonomics, but it makes the slow outage the only option. That is what every lock().unwrap() does today, and the issues above should be plenty of evidence of this being a problematic behavior in light of the existence of catch_unwind.

The post In defense of lock poisoning is the best argument for the other side and worth reading but I believe the evidence all points the other way, and most of what Oxide ships aborts on panic anyway which is also a reasonable behavior.
